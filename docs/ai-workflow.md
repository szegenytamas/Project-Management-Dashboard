# AI-assisted workflow

This project was built with **Claude Code** as a pair programmer and mentor. This file
documents how: what was delegated, what I reviewed or verified myself, what I decided or
changed, and why. The conventions the AI works under are in [`CLAUDE.md`](../CLAUDE.md).

> Written by me (the developer) after each phase, in my own words.

## How I work with the AI

- Claude Code writes code and explains each step; **I run all git commands myself**
  (branches, commits, pushes, pull requests) and review every change before committing.
- Every phase ends with passing checks (`uv run tox`) and a green CI run before I merge.
- After each phase I study a generated study guide and a decision document
  (alternatives and trade-offs) so I can explain every part of the system.
- **In AWS I run every command that creates, changes or deletes a resource myself.** The AI
  writes and explains the commands and may only run read-only checks (describe/list/get).
  Secrets (passwords, keys) are never pasted into the chat.

| Skill / tool | Used for                                                     |

## Phase 3 – Authentication

- **Delegated:** I delegated AI to solve authentication and authorization problem for the task, registration and input validation, password hashing and salting, protect endpoints.
- **Reviewed / verified myself:** Like at every phase I handle git and review and check the application that its working.
  - I tried registration and login in Swagger and checked that a wrong password and an
    unknown login return the same error.
- **Decided or changed:** Decided to have stricter password constraints at registrations.
  - After sharing the evaluation criteria with the AI, I set the rule: 12–128 characters,
    upper- and lowercase letters, a digit and a special character, and the password must not
    contain the login.

## Phase 4 – Projects, invitations, permissions

- **Delegated:**

    rejects. The fix changed the password and made `curl` print the error body

- **Decided or changed:**

  - I reviewed the evaluation criteria with the AI and adopted its suggested changes with my

    visible) and this file as a workflow description instead of a command log.

## Phase 7 – Size-limit Lambda and AWS deployment

- **Delegated:**
  - The S3-triggered Lambda (plain SQL, no ORM) with its tests, verified TLS to the database,
    the IAM policies and server scripts in `infra/aws/`, and the step-by-step instructions for
    building the AWS environment.
- **Reviewed / verified myself:**
  - I created every AWS resource myself (VPC, S3, RDS, IAM roles, EC2, Lambda) following
    the instructions, and checked each step before moving on.
  - I ran the scenario in Swagger against the deployed API, ran the bypass test (a file
    uploaded directly into S3 above the limit was deleted by the Lambda) and took the
    screenshots for `docs/aws.md`.
  - The first Lambda version failed in AWS. From its CloudWatch error we found that a new
    version of an indirect dependency broke the database driver, only over TLS. The fix pins
    all dependencies from the lock file, and a new test connects over TLS.
  - My EC2 instance first had an unencrypted disk and missing tags; I relaunched it and
    turned on default disk encryption for the account.
- **Decided or changed:**
  - A custom VPC with private subnets for the database and the Lambda (my idea), instead of
    AWS's default network.
  - I run all AWS commands that change resources myself; the AI only runs read-only checks.
  - Region eu-north-1 and a 30 USD monthly budget alert, so costs stay visible.
  - I set up a separate IAM user for the work instead of using the root user.

## Phase 8 – Extensions

### 8a – Seed data and migration test

- **Delegated:**
  - A seed script with demo users, projects and documents (`python -m project_dashboard.db.seed`)
    and a "stairway" test that runs every migration up, down and up again.
- **Reviewed / verified myself:**
  - I checked that the seed goes through the same service functions as the API, so the demo
    data follows every rule (hashed passwords, one owner, files in S3, correct totals), and
    that running it twice changes nothing.
- **Decided or changed:**
  - I agreed that production has no default demo password: the seed refuses to run there
    unless `SEED_PASSWORD` is given, because the repository is public.
  - I decided to write one study guide for the whole of Phase 8 instead of one per part.

### 8b – Continuous deployment

- **Delegated:**
  - The deploy job in CI, the IAM trust and permission policies, the SSM deploy document and
    the documentation.
- **Reviewed / verified myself:**
  - I set up the AWS side myself in the console: the GitHub identity provider, the deploy
    role with its policies, and the SSM document. I also created the GitHub `production`
    environment (only `main`, three variables) before merging.
  - Before letting CI use it, I ran the deploy document by hand in Run Command, and I tried
    to inject a command (`latest;reboot`). AWS rejected it because of the document's
    pattern - the test I wanted to fail did fail.
  - The first automatic deploy failed with "Not authorized to perform
    AssumeRoleWithWebIdentity". The rejected attempt in CloudTrail showed that GitHub sends
    an **immutable subject** with numeric owner and repository IDs, while the trust policy
    expected the name-only format. I updated the trust policy, re-ran the job, and the next
    merge deployed on the first try.
  - My commits once landed on `main` instead of a branch. They were not pushed yet, so I
    moved them to a branch and kept the pull-request workflow.
- **Decided or changed:**
  - I chose to do the AWS steps in the console instead of the CLI, using the same JSON files
    from the repository, so the live configuration matches the repo (checked afterwards).
  - Kept the immutable OIDC subject instead of switching it off, because numeric IDs cannot
    be reused by a re-created repository.

### 8c – Security hardening

- **Delegated:**
  - Rate limiting for login and registration, security headers, optional CORS, dependency
    and secret scanning in CI, and an OWASP API Top 10 checklist (`docs/security.md`).
- **Reviewed / verified myself:**
  - I removed the two setup-only secrets from the EC2 role in the console before merging;
    the automatic deploy then proved the API still works with the smaller role.
  - The live server sends the security headers and answers the 11th failed login in a
    minute with 429.
  - sudo docker logs api --tail 20 shows: real client IPs
- **Decided or changed:**
  - No Dependabot pull requests: I want to stay the only contributor in the history, so
    vulnerabilities are found by `pip-audit` in CI instead.
  - HTTPS is left as a documented gap, because it needs a domain name first.

## Phase 9 – Web UI

- **Delegated:**
  - A browser UI in plain HTML, CSS and JavaScript (no framework, no build step), served by the
    API at `/app/` with its own Content-Security-Policy, and later a design pass: logo and
    colours, project cards, drag-and-drop upload with a progress bar, loading and empty states,
    and a storage bar per project.
- **Reviewed / verified myself:**
  - I signed in to the live UI with the demo accounts and went through the main flows.
  - My first login attempts failed: the API log showed `401` (wrong password) and `409` (I
    tried to register `alice`, who already existed).
  - On the server, `alice` and `bob` already existed from my Phase 7 tests, so the seed kept
    their old passwords and only `carol` got the new one. We added `--reset-passwords`, which
    changes only the three demo accounts.
  - The first reset did nothing: the seed's output still had the old format. The server's local
    `:latest` image was old, because continuous deployment pulls `sha-<commit>` images, and
    `docker run` does not download an image it already has. Running the seed with the API's
    running image fixed it, and the docs now say so.
  - One pull request was closed by mistake instead of merged; I reopened and merged it.
- **Decided or changed:**
  - Decided on four design improvements: a clearer visual identity, drag-and-drop upload with
    progress, loading and empty states, and a storage bar.
    I left the browser's own confirmation dialogs as they are.
  - The UI only hides buttons a participant may not use; the API still decides every
    permission.
